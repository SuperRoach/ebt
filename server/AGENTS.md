# Working on the tracking API

Use the [root guide](../AGENTS.md) for cross-component changes and test commands.

- [`app.ts`](src/app.ts) owns Fastify routes, auth, CORS and WebSocket broadcasts. [`ingest.ts`](src/ingest.ts) owns SQLite writes and capture deduplication. [`devices.ts`](src/devices.ts) owns device IDs and key hashes. [`telemetry-listener.ts`](src/telemetry-listener.ts) exposes the upload-only LAN listener, and [`simulator.ts`](src/simulator.ts) exercises the ingest route. Use [API integration tests](test/api.test.ts) for schema, migration and delivery behavior.
- The [wire schema](../shared/telemetry-v1.schema.json) accepts valid positions with unknown speed, heading, satellite count or battery voltage as `null`. Keep `gpsStatusReason` optional and scoped to no-fix reports. The server logs the reason for newly stored reports. Preserve existing capture hashes when adding optional fields, and preserve the distinction between GPS capture time and server receipt time when analyzing replays.
- Production runs as `ebt` on Fly.io. SQLite and private firmware binaries are under `/data`. For migrations that rebuild tables, check volume capacity and take a snapshot before deploying. Verify `/health` and reads of existing telemetry after deployment, then assign firmware requiring the new schema. Validate with the integration suite or an unauthenticated schema probe to avoid synthetic production records.
- The admin firmware upload associates a version and binary with one device. Only that device's key can fetch the assigned binary. The API can offer the update on either transport, and the tracker downloads over Wi-Fi. A matching firmware version can mark the assignment succeeded before the board has confirmed the boot. Verify a fresh report from the new version again after the three-minute trial window, especially if an older version appears later. A fresh no-fix ping can confirm the running version because those pings bypass the microSD queue.
